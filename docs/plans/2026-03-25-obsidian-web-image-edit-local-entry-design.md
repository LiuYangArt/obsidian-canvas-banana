# Obsidian 图片本地网页编辑（基于 Local Entry）设计方案

- 日期：2026-03-25
- 状态：Draft
- 关联仓库：
1. `LiuYangArt/obsidian-canvas-banana`（主落地仓）
2. `LiuYangArt/sutu`（依赖仓，参考 Issue #228）

## 1. 背景

当前需求是：在 Obsidian 中选中或打开一张图片后，能通过网页编辑器完成编辑并写回 Vault 原文件，形成“Obsidian -> 网页编辑器 -> Obsidian”的闭环体验。

已知事实：

1. 浏览器线上 HTTPS 页面无法直接访问本地明文端口（历史问题已在 `sutu` 侧复盘）。
2. YACD 的核心思路不是“绕过限制”，而是“本地 HTTP 入口 + URL 参数驱动本地服务连接”。
3. Obsidian 插件具备 Vault 读写权限，是最自然的数据权限桥接层。

## 2. 结论（先给答案）

采用“Obsidian 插件主导的 Local Entry 模式”：

1. 插件负责启动本地会话和本地服务。
2. 插件负责把目标图片安全地暴露给网页编辑器（仅本机会话、短时 token）。
3. 编辑完成后由插件写回 Vault。

换句话说：

1. YACD 方案可借鉴“本地入口和参数化连接”。
2. 但必须补一层 Obsidian 插件 API，才能安全读写 Vault 图片。

## 3. 为什么不直接用线上网页

不是“能不能写代码”的问题，而是运行时安全模型问题：

1. 在线 HTTPS 页面默认不能访问本地明文 `http://` / `ws://` 服务。
2. Vault 文件系统权限在 Obsidian 进程里，不在普通网页里。
3. 因此必须走“本地入口 + 插件桥接”路径，才能既可用又可控。

## 4. 方案选型（含取舍）

### 方案 A：插件本地入口 + 本地网页编辑器（推荐）

效果：

1. 用户在 Obsidian 内点击“Web 编辑当前图片”。
2. 插件生成会话，打开本机本地入口 URL。
3. 网页编辑完成后通过本地 API 回写 Vault。

优点：

1. 改造成本可控，复用既有 Web 编辑器能力。
2. 权限边界清晰，安全策略可实现。
3. 与 `sutu` Local Entry 方向一致，可形成长期统一模式。

代价：

1. 需要维护一个本地会话服务层。
2. 跨仓协同（插件仓 + `sutu` 仓）需要明确接口。

### 方案 B：插件内嵌 WebView 编辑器

效果：

1. 不弹浏览器，直接在 Obsidian 视图内编辑。

优点：

1. 交互一体化最好。

代价：

1. 工程复杂度高，调试成本高。
2. 与现有 Web 版复用路径偏离，维护压力更大。

### 方案 C：导出-手工编辑-导入

优点：

1. 几乎不用开发。

代价：

1. 用户流程很重，不符合本次目标。

最终建议：优先实施方案 A。

## 5. 目标与非目标

### 目标

1. 从 Obsidian 一键打开图片进入网页编辑。
2. 编辑后一键写回原文件路径（或明确另存为新文件）。
3. 全程仅本机 loopback 通信，具备 token 会话鉴权。
4. 失败时可恢复，不破坏原文件。

### 非目标

1. 本期不做跨机器协作编辑。
2. 本期不做公共云中转。
3. 本期不做完整多人协作冲突合并。

## 6. 关键交互流程

1. 用户在 Obsidian 中选中图片附件，执行命令 `Edit image in web editor`。
2. 插件创建一次性会话（`sessionId` + `token` + `expireAt`）。
3. 插件打开本地 URL，例如：
`http://127.0.0.1:27124/app?mode=obsidian-image-edit&session=<id>&token=<token>`
4. 网页端使用 `session/token` 向本地 API 请求图片内容。
5. 用户编辑并点击保存。
6. 网页端提交二进制或 base64 到本地 API。
7. 插件执行写回：
   - 默认覆盖原路径（先备份临时文件）
   - 可选“另存为副本”
8. 写回成功后插件发 Notice，并刷新 Obsidian 视图。

## 7. 架构与职责

### 7.1 `obsidian-canvas-banana` 职责（主）

1. 命令入口、上下文解析（当前文件/当前选中图片）。
2. 本地会话管理（创建、过期、销毁）。
3. 本地 HTTP API（仅 `127.0.0.1`）和鉴权。
4. Vault 读写与回写安全策略。
5. 错误提示和用户反馈。

### 7.2 `sutu` 职责（依赖）

1. 提供支持 `mode=obsidian-image-edit` 的 Local Entry 页面能力。
2. 提供可加载外部图片字节并导出编辑结果的前端契约。
3. 保证 Web 本地入口与 `sutu#228` 方案一致。

## 8. 本地 API 合同草案（插件侧）

以下为建议合同，实际字段可在实现前冻结：

1. `GET /health`
   - 返回服务状态与版本。
2. `GET /v1/session/:id/meta`
   - 返回会话元信息（文件路径 hash、mime、尺寸、过期时间）。
3. `GET /v1/session/:id/image`
   - 返回原图二进制。
4. `POST /v1/session/:id/save`
   - body: 编辑后图片二进制 + `saveMode`（`overwrite`/`save_as`）。
   - 返回：写回后的 vault 路径。
5. `POST /v1/session/:id/cancel`
   - 取消会话并清理临时资源。

鉴权规则：

1. 每个请求必须带 `Authorization: Bearer <token>`。
2. token 与 session 绑定，TTL 默认 10 分钟。
3. 超时或校验失败返回 `401/403`，不暴露真实文件路径。

## 9. 数据与安全策略

1. 服务仅监听 `127.0.0.1`，禁止 `0.0.0.0`。
2. token 从 URL 读取后，前端应立即清理地址栏参数。
3. 插件日志里禁止输出明文 token。
4. 覆盖写回前先生成临时备份（同目录隐藏后缀或内存快照）。
5. 写回失败时必须保留原图并给出回滚提示。

## 12. 验收标准

1. 在 Obsidian 中可一键打开当前图片到网页编辑器。
2. 编辑后可成功写回 Vault 原图，Obsidian 预览刷新正常。
3. token 过期、无 token、错误 token 均会被拒绝且提示清晰。
4. 覆盖保存失败时原图不损坏。
5. Local 服务停止后，命令会给出明确重试提示。

## 13. 测试计划

### 自动化（插件侧优先）

1. 会话生命周期测试（创建、过期、销毁）。
2. token 校验测试（正确/错误/过期）。
3. `save` 写回测试（overwrite/save_as/失败回滚）。

### 手工验证

1. 打开 png/jpg/webp 三类图片分别编辑并保存。
2. 验证 Obsidian 同目录资源与链接是否保持正确。
3. 连续 20 次快速打开与保存，确认无端口泄漏和僵尸会话。

## 15. 风险与缓解

1. 风险：端口冲突导致入口失败。
   缓解：自动选取空闲端口并回显实际 URL。
2. 风险：用户误把线上站点当成本地入口。
   缓解：命令始终打开本地 URL，不暴露线上直连入口。
3. 风险：大图写回造成 UI 卡顿。
   缓解：保存路径异步化 + 进度提示 + 超时提示。
